# 자연스럽고 읽기 쉬운 한국어

글은 처음 보는 독자 기준으로 쓴다. 작성자가 아는 맥락, 작업 중 만든 이름, 저장소 구조를 독자도 안다고 가정하지 않는다. 형식이 달라도(대화 답변, 문서, 커밋 메시지) 같은 기준을 적용한다. 산출물 형식을 따로 정하는 스킬이 있으면 그 형식이 우선하고, 이 스킬은 그 형식이 정하지 않은 부분에 적용한다.

## 쓰기 전에 정한다

1. 독자: 누가 읽는가, 무엇을 알고 무엇을 모르는가.
2. 결론: 독자가 다 읽은 뒤 기억해야 할 한 문장.
3. 전달 범위: 같은 맥락 안에서 읽는 글인가, 저장소·대화 밖으로 나가는 글인가.

## 구조와 형태

- 결론을 앞에 둔다. 긴 글은 한눈에 보기(무엇을 했나, 결과, 가장 중요한 발견) → 배경 → 방법 → 결과 → 해석과 한계 → 다음 단계 순서이고, 짧은 글은 결론 한두 문장 뒤에 근거를 붙인다.
- 흐름이 있는 작업(실험, 디버깅, 설계 변경)은 시간 순서로, 단계마다 본 것과 결정과 결과를 연결한다.
- 독자의 판단에 필요한 내용만 둔다. 중복 설명, 작업 중 독백, 상투적 문구를 지우고 같은 경고는 한 곳에만 쓴다.
- 문단은 짧게, 한 문단에 한 논점. 목록은 나란한 항목일 때만, 표는 같은 기준으로 비교할 때만 쓴다. 인과를 목록으로 조각내지 않는다.
- 로그 전문이나 기계 출력을 본문에 붙이지 않는다. 필요한 줄만 발췌한다.
- 추상 설명보다 구체 예시와 수치를 먼저 보인다. 기술 지표는 "100건 중 몇 건"처럼 풀어 쓰고, 작업 중 만든 이름과 약어는 설명 없이 쓰지 않는다.
- 확인한 사실과 해석을 구분한다.

## 한국어 문장을 교정한다

영어를 먼저 떠올려 문장을 만들면 영어 구조가 한국어 단어에 얹힌다. 단어는 한국어인데 문장이 어색하면 번역투다. 한국어는 주어를 자주 생략하고, 용언으로 문장을 끌고 가며, 피동보다 능동을 쓴다. 고치려는 문장을 소리 내어 읽는다는 기분으로 걸리는 곳을 찾고, 단어만 바꿔 해결되지 않으면 문장 구조를 바꾼다.

### 사물·추상 명사를 행동하는 주어로 쓰지 않는다

주어가 그 동작을 실제로 하지 않으면 상태 서술로 고친다. 프로그램·서버·함수처럼 실제로 동작하는 주어("서버가 요청을 거부한다")는 그대로 둔다.

1. 사물이 막다·만들다·정하다·말하다·보여 주다·이끌다·지키다 같은 행동을 하면, 무엇이 어떤 상태인지 먼저 쓰고 결과를 잇는다. "X가 말해 준다(X says)"는 "X에 정해져 있다", "X에 나와 있다"로 쓴다.
   - 전: 절마다 정의가 있어, 스킬에 있어야 할 내용이 ADR로 새는 것을 형식이 막는다.
   - 후: 절마다 작성할 내용이 정해져 있어, 결정의 동작 절차는 스킬에만 남고 ADR에는 섞이지 않는다.
2. 결정·판단·감수는 사람이 한다. 문서·절·표는 결정이 기록된 위치이므로 주어로 세우지 않고 "~에서"로 적는다. "그대로다", "같다"에는 무엇과 같은지 밝힌다.
   - 전: 2022년 질의는 21.8%가 제외되어 9월 2주차 4-2절이 감수하기로 한 그대로다.
   - 후: 2022년 질의는 21.8%가 제외되었으며, 이는 9월 2주차 4-2절에서 감수하기로 정한 손실과 같다.
3. 결정·선택·변경·도입 같은 명사를 주어로 세워 "~은 ~하는 것이다"로 맺은 문장은 조건("~하면")과 결과("~해야 한다")로 푼다.
   - 전: 이전 메시지만 정답 후보로 삼는 결정은 이 손실을 감수하는 것이며, 정답 0건 질의의 처리 규칙이 따로 필요함.
   - 후: 이전 메시지만 정답 후보로 삼으면 이 손실은 감수해야 하며, 정답 0건 질의를 처리하는 규칙도 따로 정해야 함.

## 외부 전달 글은 그 글 하나로 완결한다

저장소·대화 밖으로 나가는 글에는 저장소 경로, 파일명, 스크립트·함수명, 실행 ID, 해시, 브랜치, 내부 코드네임, 저장소 주소, 상대 링크, 로컬 이미지 경로를 넣지 않는다. 원본이 근거라면 "원본은 별도로 보관하며 요청 시 제공할 수 있다"처럼 존재와 제공 방법만 적는다. 저장소 안 문서는 근거 파일로 링크할 수 있지만, 본문은 링크를 열지 않아도 이해되어야 한다.
