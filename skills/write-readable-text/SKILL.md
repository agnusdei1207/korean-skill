# 읽기 쉬운 글쓰기

사람이 읽는 글은 예외 없이 처음 보는 독자 기준으로 쓴다. 작성자가 아는 맥락, 작업 중 만든 이름, 저장소 구조를 독자도 안다고 가정하지 않는다. 이 원칙을 어긴 글은 내용이 정확해도 미완성이며, 완료로 보고하지 않는다. 대화 답변, 문서, 커밋 메시지처럼 형식이 달라도 같은 기준을 적용하고, 사람이 읽지 않을 것 같은 글도 언젠가 사람이 읽으므로 예외를 두지 않는다.

산출물 형식을 따로 정하는 스킬이 있으면 그 형식이 우선하고, 이 스킬은 그 형식이 정하지 않은 부분에 적용한다.

## 함께 쓰는 스킬

- [읽기 쉬운 한국어 문장](../readable-korean-sentences/SKILL.md): 한국어 문장 교정.
- [문장결 — 흐름과 변주](../prose-flow-and-variation/SKILL.md): 문단 흐름, 문장 변주, 반복 통제.

## 쓰기 전에 정한다

1. 독자: 누가 읽는가, 무엇을 이미 알고 무엇을 모르는가. 외부 전달 글이라면 해당 분야 전문가이지만 이 작업과 코드는 모르는 사람으로 가정한다.
2. 독자의 질문: 이 글을 읽는 사람이 가장 먼저 알고 싶은 것 세 가지.
3. 결론: 독자가 다 읽은 뒤 기억해야 할 한 문장.
4. 전달 범위: 같은 맥락 안에서 읽는 글인가, 저장소·대화 밖으로 나가는 글인가.

독자가 글 밖의 지식 없이 한 번 읽고 이해할 수 있어야 한다. 정확성과 쉬움이 충돌하면 정확한 내용을 쉬운 말로 풀어 쓰고, 정확성을 버리지 않는다.

## 구조

- 결론을 앞에 둔다. 긴 글은 한눈에 보기(무엇을 했나, 결과 몇 줄, 가장 중요한 발견) → 배경 → 방법 → 전개 → 결과 → 해석과 한계 → 다음 단계 → 부록 순서를 기본으로 하고, 짧은 글은 결론 한두 문장 뒤에 근거를 붙인다.
- 흐름이 있는 작업(실험, 디버깅, 설계 변경)은 시간 순서로 쓴다. 단계마다 무엇을 보았고, 그래서 무엇을 결정했고, 결과가 어땠는지를 연결한다.
- 독자의 판단에 필요한 내용만 둔다. 문장·표·절마다 독자의 질문에 답하는지 확인하고, 중복 설명·작업 중 독백·상투적 문구·불필요한 예시는 삭제한다. 세부 근거는 필요할 때만 부록으로 둔다.
- 같은 경고·한계는 한 곳에만 쓴다.

## 읽기 쉬운 형태

- 제목을 쓰는 글은 제목만 훑어도 흐름이 보이게 하고, 제목 하나 아래에는 한 주제만 둔다.
- 문단은 짧게, 한 문단에 한 논점. 세 줄을 넘는 문장 덩어리는 나누거나 목록으로 바꾼다.
- 목록은 나란한 항목일 때만, 표는 여러 대상을 같은 기준으로 비교할 때만 쓴다. 문장으로 이어져야 할 인과를 목록으로 조각내지 않는다.
- 로그 전문·기계 출력 덤프를 본문에 붙이지 않는다. 필요한 줄만 발췌하고 나머지는 위치만 적는다.
- 숫자·날짜·단위는 독자가 바로 읽는 형식으로 쓴다(`2026-10-19`, `p95 120ms`, `3건 중 2건`).

## 표현

- 추상 설명보다 구체 예시를 먼저 보인다. 실패나 차이를 설명할 때는 입력, 기대한 결과, 실제 결과, 그렇게 된 이유를 나란히 놓는다.
- 처음 나오는 개념은 비유나 한 줄 풀이로 연다. 비유는 개념당 한 번만 쓴다.
- 지표는 독자의 언어로 쓴다. F1, TN/FP 같은 기술 지표는 "100건 중 몇 건"처럼 풀고, 원래 이름은 필요할 때 괄호로 한 번 병기한다.
- 작업 중 만든 이름·약어·의미 없는 식별자(사례 번호, 내부 ID, 임시 값)는 설명 없이 쓰지 않는다. 읽기 쉽게 다듬은 예시는 다듬었다는 사실과 원래 형태를 함께 적는다.
- 확인한 사실과 해석을 구분한다. "말할 수 있는 것"과 "조심해서 말해야 하는 것"을 분리해 쓴다.

## 외부 전달 글의 의존성 제거

저장소·대화 밖으로 나가는 글은 그 글 하나로 완결되어야 한다.

- 저장소 경로, 파일명, 스크립트·함수명, 실행 ID, 해시, 브랜치, 내부 코드네임, 저장소 주소를 본문에 넣지 않는다.
- 원본 데이터·코드가 근거라면 "원본은 별도로 보관하며 요청 시 제공할 수 있다"처럼 존재와 제공 방법만 적는다.
- 상대 링크, 내부 앵커, 로컬 이미지 경로를 쓰지 않는다. 그림이 필요하면 글과 함께 전달되는 형태로 넣는다.
- 파일로 전달하면 파일명은 독자가 알아보는 이름으로 짓는다.

저장소 안 문서는 근거 파일로 링크할 수 있다. 다만 본문의 설명은 링크를 열지 않아도 이해되어야 하고, 링크는 확인 수단으로만 쓴다.

## 마크다운일 때 추가 규칙

- 코드 블록은 실제 명령·코드·출력 발췌에만, 코드 표시는 독자가 실제로 입력할 명령·코드·식별자에만 쓴다.
- 완료 보고 전에 바꾼 md 파일 전체를 서식 검사하고, 결과가 0건일 때만 완료로 본다.

```text
grep -nE '\*\*[^*]+\*\*|__[^_]+__|<(span|b|strong|em|i|u|font|mark)[ >]|style=' <바꾼 md 파일들>
```

코드 블록·인라인 코드 안의 리터럴(예: 위 검사식 자체, 코드 예시의 `**kwargs`, 규칙을 설명하려고 적은 태그 이름)은 서식이 아니므로 제외하고 판정한다. 산출물 형식이 굵은 표기를 기능으로 요구하는 경우는 해당 도메인 스킬이 명시적으로 소유할 때만 예외다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "읽는 사람도 맥락을 안다" | 기준 독자는 처음 보는 사람이다. 맥락이 필요하면 글 안에 둔다 |
| "정확하게 쓰려면 전문 용어가 필요하다" | 정확한 내용을 쉬운 말로 풀고, 원래 용어는 처음 한 번 병기한다 |
| "경로를 적어 두면 찾아볼 수 있다" | 외부 독자는 저장소에 접근할 수 없다. 외부 전달 글은 그 글 하나로 완결된다 |
| "중요하니 굵게 강조하자" | 굵은 표기는 원문에서 잡음이다. 결론을 앞에 두고 제목·목록으로 드러낸다 |
| "짧은 답변이라 기준이 필요 없다" | 짧을수록 결론 하나와 근거 하나가 분명해야 한다. 같은 기준을 압축해 적용한다 |
| "AI만 읽는 글이다" | 사람이 언젠가 읽는다. 같은 기준으로 쓴다 |

## 위험 신호

- 배경부터 시작해 결론이 끝에 있는 구조
- 작업 중 만든 이름·약어·내부 ID가 설명 없이 등장
- 외부 전달 글의 경로·파일명·저장소 주소·상대 링크
- 구체 예시·수치 없는 주장, 풀이 없는 기술 지표
- 사물·추상 명사가 행동하는 주어로 쓰인 한국어 문장
- 세 줄을 넘는 문장 덩어리, 본문에 붙인 로그 전문
- 마크다운의 굵은 표기, 인라인 HTML 서식, 명령이 아닌 곳의 코드 표시

## 종료 게이트 (다 쓴 뒤 검수)

작성자 시점을 버리고 처음 보는 독자로서 처음부터 다시 읽는다. 하나라도 아니면 고친다.

- [ ] 첫 문단만 읽어도 무엇을 했고 결과가 무엇인지 알 수 있는가.
- [ ] 모든 문장이 글 밖 지식 없이 이해되는가. 작업 중 만든 이름·약어가 설명 없이 남아 있지 않은가.
- [ ] 핵심 주장마다 구체 예시나 수치가 붙어 있는가.
- [ ] 기술 지표와 전문 용어가 처음 나올 때 풀이되어 있는가.
- [ ] 같은 경고·설명이 여러 곳에 반복되지 않고, 긴 문장 덩어리·로그 덤프가 없는가.
- [ ] 한국어 글이라면 사물·추상 명사 주어 문장을 점검했는가.
- [ ] 외부 전달 글이라면 경로·파일명·내부 이름·저장소 주소가 하나도 없는가.
- [ ] 수치가 근거 자료와 일치하는가.
- [ ] 마크다운이라면 서식 검사가 0건인가.
